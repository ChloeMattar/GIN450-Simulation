Who controls refresh?
  1. Device specification
  2. Firmware configuration
  3. Memory controller
  4. DRAM

The manufacturer’s datasheet sets the refresh requirement for each temperature range. Firmware configures the memory controller to meet it, the controller schedules refresh commands during normal operation, and the DRAM’s own internal circuitry performs self-refresh when the controller is not issuing commands.

How it works

Each DRAM cell stores a bit as charge that leaks away. Heat makes it leak faster, so the datasheet requires a shorter refresh window when hot.

The refresh window (64 ms or 32 ms) is the time in which every row must be refreshed. It is split into 8,192 refresh commands. The average command interval (tREFI) is the window divided by 8,192. One command refreshes only a small slice of the chip, so the commands gradually cover everything.

Missing a deadline means retention is no longer guaranteed. It does not mean a bit flips at once. In this model a bit is lost only when its charge falls below 50%, and a later refresh cannot bring the original value back.

Timing assumptions

Device: Micron 1Gb DDR3 SDRAM. Datasheet: 64 ms, 8,192-cycle refresh at 0 °C to 85 °C, and 32 ms at 85 °C to 95 °C (case temperature, TC). Average intervals: 64 ms ÷ 8,192 = 7.8125 µs and 32 ms ÷ 8,192 = 3.90625 µs. Other devices use other values.

Sample grid: 4 rows × 8 cells. Each row stands for 2,048 commands of the 8,192-command sequence, and each cell is refreshed once per sequence.

Teaching model, not calibrated: a cell’s charge halves in a retention time of 96 ms at 85 °C, halved for every 10 °C hotter, scaled by a fixed per-cell factor from 0.8 to 1.3. Charge below 50% counts as a modeled bit error.

Simplifications: the model advances in 0.5 ms steps, the controller reacts the instant TC crosses 85 °C and refreshes all sample cells in a catch-up (counted as 4 commands), and the datasheet’s allowance for bunching commands is ignored. Animation speed never changes these results.
